## 1. 核对依据和已固定决策

本 checklist 核对了：

- 本地 DFlash2 checkpoint revision `50307d4c4cde6860d4eee73e2547cd786fe8e8a4`；
- 本地 vLLM `qwen3_dflash2.py` 和 V2 DFlash2 speculator；
- 本地 SGLang `dflash.py` 和 `dflash_worker_v2.py`；
- NInfer 现有 DFlash 实现、公共 Op 合同和当前 production route table；
- git 历史中 `841ae5ec` 的 35B-A3B DFlash Op checklist 和 `5b5cbea4` 的
  Qwen3.8 NVFP4 Op checklist。

历史 checklist 提供现有 Op 和 route inventory；本表中的 DFlash2 geometry 取自当前
checkpoint 与参考实现。

以下决策是本次 Op 实现的硬边界：

1. DFlash2 proposal 每个 request 始终计算完整 `1 anchor + 7 masks`；不用较短 block
   代替原生八列 block。
2. Dynamic convolution 必须在两个 public 语义边界融合：前端是
   `RMSNorm + coefficient projection + input-side convolution`，后端是
   `W8 projection + output-side convolution + residual add`。Program 不观察完整 delta 或 raw output
   projection。Private materialization 只能作为同一 public Op 内部 route，并由 workspace query
   完整申报。
3. Q/K 的 plain head RMSNorm 和 1-D full-head RoPE 合并为一个 Op；原始 Q/K 原地
   更新，不再为 normalized Q/K 分配第二份大 buffer。
4. Proposal head 必须直接产生 top-16，不物化 `[248320,7B]` 或
   `[131072,7B]` 的 dense proposal logits。Target verify 仍保留 dense logits，因为 target
   sampling 和 `(p-q)+` correction 需要完整 `p`。
5. Selector 的数学定义包含完整 `[B,7,16,16]` edge lattice；production Op 只计算当前
   已选 predecessor 对应的 16 个 edge，边计算边向左到右 walk。
6. DFlash2 stochastic proposal 产生的 sparse FP32 `q` 直接交给共享
   speculative-accept 语义。
7. Context 路径采用 `feature linear -> context norm -> context_kv_materialize`。最后一个
   public Op 消费五层 QKV parent 的 K/V row views、五组 K norm、positions/counts 和五个
   cyclic cache，完整拥有 K/V projection、K norm/RoPE、V 的 FP16 storage cast 与 append
   state transition。它不要求 runtime weight repack 或 artifact 中的重复 K/V；multi-parent
   grouped/fused 与现有 composed 计算都是该 Op 的内部 route。
8. Target hidden capture 使用独立 `scatter_bf16_batch`，在五个指定 layer 写入
   lane-owned feature storage。

## 2. 固定 workload 与 shape 记号

| 符号 | 含义 | 值 |
|---|---|---:|
| `B` | active requests | `1..8` |
| `W` | DFlash2 proposal/verify 物理宽度 | `8` |
| `K` | proposal 数 | `7` |
| `T` | existing matrix Op 的公共 column extent | 任意正整数 |
| `T_8` | 将 `[*,8,B]` 展平后的列数 | `8,16,24,32,40,48,56,64` |
| `T_7` | 七个 mask hidden 展平后的列数 | `7,14,21,28,35,42,49,56` |
| `P_b` | request `b` 当轮允许验证的 draft extent | `0..7` |
| `Q_b` | target verify live input columns | `P_b+1`, `1..8` |
| `A_b` | request `b` 经 target 验证后接受的 draft 数 | `0..P_b` |
| `L_b` | target 授权的 provisional output 数 | `A_b+1`, `1..8` |
| `N_b` | Frontend 最终提交的 output/input-prefix 数 | `0..L_b` |
| `N_lane` | startup-fixed pending-feature request-lane capacity | `1..8`，且 `B<=N_lane` |
| `S_state` | StateImage slot capacity | startup-fixed，且 `>=B` |
| `T_c` | context materialization 的物理列数 | decode 为 `T_8`；prefill 为 `1..min(prefill_chunk,2048)` |

共享的固定维度是：

```text
H=5120, I=17408, H_f=25600
Q=32 heads x 128 = 4096
K/V=8 heads x 128 = 1024
dynamic groups=320, group width=16, taps=2, sides=2
selector rank=256, candidates=16
physical vocab=248320, valid full-head rows=248077, optimized rows=131072
```

`T_8` 和 `T_7` 是矩阵 Op 的物理 extent。Dynamic convolution、non-causal attention、target
GDN record/replay 仍保留 `[rows,W,B]` 中的 request 边界；不能只把它们当成
`[rows,W*B]` 的无结构矩阵。

本文的矩阵 `Weight [N,K]` 使用 artifact 的逻辑 `[output rows,input columns]` 记法；普通
runtime `Tensor` 使用 NInfer `ne[]` 次序，`ne[0]` 是连续轴。两个容易混淆的 stored tensor
明确为：

```text
artifact base_kernel [side,tap,channel] = [2,2,5120]
runtime Tensor view                     = [5120,2,2]

artifact selector codebook [vocab,rank] = [248320,256]
runtime Tensor view                     = [256,248320]
```

## 3. 完整 Op 调用账本

### 3.1 Target feature 到 DFlash2 context

| 阶段 | 数学输入 | 输出/效果 | 每次 append 调用 | 归属 |
|---|---|---|---:|---|
| ragged gather | source `BF16 [25600,8,N_lane]` + lane/start/end | `BF16 [25600,8,B]`, positions/counts | decode 1, prefill 0 | `OP-Q02` |
| feature projection | `BF16 [25600,T_c]`, W8 `[5120,25600]` | `BF16 [5120,T_c]` | 1 | `OP-E01` |
| context norm | `BF16 [5120,T_c]` | `BF16 [5120,T_c]` | 1 | `OP-Q04` |
| five-layer context materialization | normalized context + five K/V pairs + K norms + positions/counts | five capacity-2048 K-BF16/V-FP16 rings | 1 | `OP-N07` |

Prefill 只有 `B=1`。当前 feature chunk 不超过 2048 行时全部进入 materialization；超过
2048 行时先取最后 2048 个绝对位置，因此 feature projection 和后续 K/V 只看到该 tail，
而 context frontier 仍按完整 prefill chunk 前进。Decode 在下一轮 proposal 前从 lane-owned
pending features gather 固定物理 `W=8`，`counts[b]=N_b` 决定有效前缀；物理尾部即使被
投影也不写入 cyclic cache。

### 3.2 DFlash2 proposal

| 阶段 | 输入 | 输出/效果 | 每轮调用 | 归属 |
|---|---|---|---:|---|
| masked block | anchor/position `[B]`, proposal valid columns all equal 8 | ids/positions `I32 [8,B]` | 1 | `OP-R01` |
| embedding | ids `[8,B]`, target table | residual `BF16 [5120,8,B]` | 1 | `OP-Q03` |
| attention norm/conv prepare | residual + BF16 conv weights | prepared `BF16 [5120,8,B]`, finish delta | 5 | `OP-N01` |
| attention QKV | prepared + W8 `[6144,5120]` | Q/K/V `4096/1024/1024 x T_8` | 5 | `OP-E03` |
| Q/K norm + RoPE | Q/K + two `[128]` norms | 原地 normalized/rotated Q/K | 5 | `OP-N03` pair form |
| symmetric SWA | Q/K/V + local context | attention `BF16 [4096,8,B]` | 5 | `OP-E05` |
| attention finish | attention + W8 `[5120,4096]` + delta | conv-finished residual update | 5 | `OP-N02` |
| MLP norm/conv prepare | residual + BF16 conv weights | prepared `BF16 [5120,8,B]`, finish delta | 5 | `OP-N01` |
| gate/up + SwiGLU | prepared + W8 `[34816,5120]` | activation `BF16 [17408,8,B]` | 5 | `OP-E04` |
| MLP finish | activation + W8 `[5120,17408]` + delta | conv-finished residual update | 5 | `OP-N02` |
| final norm/pack | residual `[5120,8,B]` | mask hidden `BF16 [5120,7B]` | 1 | `OP-N04` |
| proposal head | mask hidden + selected head | ids/scores `[16,7,B]` | 1 | `OP-N05` |
| selector hidden | mask hidden + BF16 `[256,5120]` | `BF16 [256,7,B]` | 1 | `OP-E02` |
| selector walk | candidates/scores/hidden/codebooks/anchor | drafts `[7,B]`, sparse `q [16,7,B]` | 1 | `OP-N06` |

在选定的融合边界下，一次 proposal 是 46 个 public Op call：轮起点 2 个、
5 层各 8 个、tail 4 个。这个数字用于后续 profile 归因，不是对 kernel
launch 数的公共承诺；一个 Op 内部可以使用多个 kernel。

## 4. Op 工作分类

### 4.1 分类判据

| 类别 | 判据 | 实现边界 |
|---|---|---|
| `N` 完全新增 | 当前没有兼容的 public semantic contract | 新增合同、wrapper、workspace/dispatch 和 production implementation |
| `E` 扩展现有 Op | 语义属于现有 Op，但当前合同或 registry 不接纳本次 format、geometry、capacity 或 proposal distribution | 修改原合同和原 family 的 validation/registry/route；不创建平行 Op |
| `Q` 仅性能 qualification | 当前 public contract、validation、适用的 workspace query 和 production route 已接纳本次精确输入 | 不修改合同、wrapper、dispatch 或 kernel；只处理 Section 7 的产品性能点 |
| `R` 直接复用 | 当前支持已覆盖，且本轮没有独立性能决策 | 只由 schedule 调用，不构成 Op 实现工作 |

`N/E/Q` 是三种不同的 Op 工作类型；`R` 只保留完整调用账本。一个 exact profile/work item
只属于一类，同一个 Op family 的不同 format 或 geometry 可以分别落在 `E` 与 `Q`。
`OP-N07` 是新的 public state-transition Op；它内部调用已有 Op 时，那些依赖仍按各自的
`E/Q` 分类处理，不改变 N07 的类别。

## 5. `N` 类新 Op 的精确合同

### OP-N01 — `rmsnorm_dynamic_grouped_conv_prepare`

状态：已完成。Production route 对 `B=1..6` 使用 split-K 8、对 `B=7..8` 使用 split-K 4；
public qualification 覆盖 `B=1..8` 的完整 prepared/finish-delta 公式和 request 边界。

输入和输出：

```text
residual       BF16 [5120,8,B]
norm_weight    BF16 [5120]
base_kernel    BF16 [5120,2 taps,2 sides]  # runtime view; artifact [2,2,5120]
kernel_weight  BF16 Weight [1280,5120]     # logical rows [side,tap,group]
prepared       BF16 [5120,8,B]
finish_delta   BF16 [320 groups,2 taps,8,B]
```

`B=1..8`，`eps=1e-6`，group width 16。完整公式是：

```text
n = plain_rmsnorm(residual, norm_weight)
d = reshape(kernel_weight @ n, [side,tap,group,8,B])

prepared[g,j,i,b]
  = (base[0,0,g,j] + d[0,0,g,i,b]) * n[g,j,i,b]
  + 1{i>0} * (base[0,1,g,j] + d[0,1,g,i,b]) * n[g,j,i-1,b]

finish_delta[g,t,i,b] = d[1,t,g,i,b]
```

公式中的 `base[s,t,g,j]` 是逻辑索引，对应 runtime
`base[g*16+j,t,s]`；不对 artifact bytes 做转置。

request 边界由 `[8,B]` 布局显式表达；`i=0` 不读取上一个 request 或上一轮的列。
Input-side delta 不是 public output；production route 不完整写出 `BF16 [1280,8,B]`。
`finish_delta` 保持到同一 sublayer 的 N02 调用结束。默认 route 直接计算所需
input-side coefficients；private materialization 是同一 Op 的 extent-specific 内部 route。

### OP-N02 — `linear_dynamic_grouped_conv_add`

状态：已完成。Public contract、wrapper、production dispatch、W8 实现、独立数值 oracle 和

注册两个 W8G32 exact problem：

```text

residual[g,j,i,b] +=
```

### OP-N05 — `linear_topk`

状态：已完成。三个 head profile 的 `B=1..8` 均已核对 FP32 score、global-id stable tie、

```text
full_head           W8/row-FP8 Weight [248320,5120]

optimized_head      Q4 Weight [131072,5120]
```

| Route | Weight | 参与 top-16 的 rows | id 语义 |
|---|---:|---:|---|
| groupwise full | W8 `[248320,5120]` | `0..248076` | row id 就是 global id |

### OP-N06 — `candidate_selector_path`

状态：已完成。Public contract、wrapper、DFlash2 proposal RNG purpose、production kernel、
独立数学 oracle 和 cold-cache CUDA Graph benchmark 均已落地。

输入：

```text
candidate_ids       I32  [16,7,B]
unary_scores        FP32 [16,7,B]
projected_hidden    BF16 [256,7,B]
anchors             I32  [B]
predecessor_table   BF16 [256,248320]  # runtime view; artifact [248320,256]
successor_table     BF16 [256,248320]  # runtime view; artifact [248320,256]
base_positions      I32  [B]
configs             device SamplingConfig[B]
```

输出：

```text
drafts              I32  [7,B]
proposal_q          FP32 [16,7,B]
```

Op 实现算法文档 Section 6 的 edge 公式和 conditional walk。每个位置只计算
已选 predecessor 的 16 个 successor score；在选定 `j_i` 后才处理下一位。
`proposal_q[:,i,b]` 是该 realized row 上的实际 16-way 概率；greedy request 写出精确
one-hot，positive-temperature request 写出 FP32 softmax。

Op 只读取 `configs[b].temperature` 和 `configs[b].seed`，并使用新增的
`kSamplePurposeDFlash2Proposal`。若 anchor 位置为 `F`，第 `i` 个 selector step 预测
`F+i+1` 的 token，counter key 是 `(seed,F+i,purpose)`。一个 batch 可同时包含 greedy
和 stochastic request。

完整 lattice 是该 Op 的数学定义；production Op 按实际前驱逐行计算并立即完成选择。

Production 固定为每 request 一个 512-thread CTA，七个位置在 CTA 内依次处理。每个 warp
负责一个 candidate；每步的 16 个 successor BF16 row 以 16-byte `cp.async` 完整搬入共享
存储，同时 256 个线程计算当前 predecessor 与 projected hidden 的逐 rank 乘积。随后 16 个
warp 分别完成 256 项 FP32 edge reduction，warp 0 进行 greedy tie-break 或 FP32 softmax、
counter-based draw，并立即把选中 token 作为下一步 predecessor。实现不生成
`[B,7,16,16]` lattice，也不分配 caller workspace。

数值 qualification 从 represented BF16 codebook/hidden 与 FP32 unary score 构造独立 FP64
完整 lattice，再执行相同的条件 walk；覆盖 B1 stochastic 和 B8 greedy/stochastic mixed
batch，draft ids 精确一致，实际 predecessor row 的 `proposal_q` 直接对数学 softmax 比较。
RTX 5090、CUDA 13.1、cold-cache、单节点 CUDA Graph、12 次 warmup/160 次计时下，
`B=1..8` 的 greedy 与 stochastic median 分别均为 `11.520 us` 和 `13.568 us`，
`B=2..8` mixed median 均为 `13.568 us`；workspace 为 0。

- decode `W_c=8,B_c=1..8` 使用两阶段 direct route。第一个 kernel 以十个独立 K/V row-view
  pointer 为 grouped parents，沿 `matrix=2*layer+K/V` 调度现有 W8 R8/C4 contraction；K 以

- `W_c=8,B_c=1` 归入 direct route。这里没有可调 token threshold、环境开关或失败回退；

Direct route 的 transient payload 是 `BF16 [5,1024,8B]`，最大 `640 KiB`；composed route
是两块 `BF16 [1024,W_c]`，`W_c=2048` 时为 `8 MiB`。`max_count=0` 整个 Op 无 launch。

实现新增 exact `speculative_accept_sparse_drafts` form，现有 one-hot form 保持原调用合同。
Sparse form 直接在 target 的最多 20 项过滤 support 上查找 16-way global candidate ids，并在
首次拒绝时原位计算 residual；不展开 dense proposal vocabulary。所有 row 均为无 penalty
greedy 时使用单-warp raw-target route，Graph 为 1 个 node、workspace 为 0；其他 mixed/
stochastic/penalty batch 使用现有 partial/group target-sampling substrate，Graph 为 2 个 nodes，
workspace 为 B1 `648,704 B`、B8 `5,189,632 B`。Sparse form 只读 token counts，写出的
round length/anchor 明确为 provisional。两个归约层级均只保留精确 top-20：每个 warp 先对
自己的 64 项排序，再以 8-way merge 合并，不再对 512 项做全块排序；无 penalty 路径在
tile 内使用包含 BF16 顺序值和 9-bit local token tie-break 的 32-bit key，写入跨 tile
workspace 前恢复为全局 key。

RTX 5090、CUDA 13.1、cold-cache CUDA Graph 下，`P=7` raw greedy 的 B1/B8 中位延迟为
`3.840/3.872 us`；counts/penalty active 的 general route 在 `P=0` 为
`19.712/46.336 us`，在 `P=7` 为 `48.384/202.016 us`。关闭 counts 后 `P=7` 为
`44.288/169.472 us`。B1..8 均已覆盖。

## 8. 融合方案汇总

| 数据流边界 | 方案 | 中间量与所有权 |
|---|---|---|
| proposal norm/coefficient/input convolution | `OP-N01` | 输出 prepared hidden 和 finish-side delta；不写完整 input-side delta |
| attention/MLP projection/output convolution/residual | `OP-N02` | residual 是 public output；raw projection 是 Op 内部值 |
| Q/K head norm 与 1-D RoPE | `OP-N03` | Q/K 原地更新，没有第二份 normalized Q/K root |
| final norm 与七列 mask pack | `OP-N04` | 直接生成 `[5120,7B]`，anchor 列不进入 proposal head |
| proposal projection 与 top-16 | `OP-N05` | 直接输出 ids/scores，不物化 dense proposal logits |
| selector edge 与 conditional walk | `OP-N06` | 逐 predecessor row 计算并保留 realized sparse `q`，不物化 full lattice |
| five-layer context update | `OP-N07` | public state transition 不输出 K/V；decode 使用 grouped-projection + fused K post/store 两阶段 direct route，prefill 使用 two-buffer composed route，均直接消费既有 QKV row views |
| target feature capture | `OP-Q05 scatter_bf16_batch` | 五个指定 layer 写入 lane-owned feature storage |
| target logits | `OP-Q10` 现有 dense output head | 完整 target distribution `p` 供 sampling 与 sparse-`q` correction 使用 |
